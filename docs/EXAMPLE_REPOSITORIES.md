# Example notebook repositories

Start with the [OpenBricks examples](../examples/), especially [Hello Spark](../examples/hello_spark.py). They use OpenBricks' supplied `spark`, `display`, and local storage conventions. External repositories are useful learning material, but importing notebook source does not reproduce a Databricks workspace or install its dependencies.

The two official upstream repositories below were inspected on November 4, 2026. The three selected files were downloaded at the recorded commits and passed through OpenBricks' actual notebook parser. **Their notebook code was not executed in OpenBricks during this review.** “Parses” confirms the import format, not successful execution or compatibility of every file in the repository.

## Import a selected file first

For the smallest trial, open a pinned file link, download its raw contents with its original extension, and use **Workspace → Import**. For `.ipynb`, download the notebook JSON rather than saving GitHub's rendered HTML page. This imports only the notebook you intend to inspect.

To exercise Git import, open **Git repositories → Clone repository**, enter the repository URL and exact branch from the table, then choose **Import notebooks** on the repository card. Source folders become workspace folders beneath the repository's folder. The current importer scans the whole repository; it does not offer a single-path selection. The clone includes the selected branch's history rather than using a shallow clone. Downloading selected files is therefore preferable when exploring a large upstream repository.

Only the files in the table were reviewed. In particular, `bundle-examples` also contains notebooks and SQL for Databricks widgets, sample catalogs, Lakeflow pipelines, dbt, and cloud services. Those are not covered by the two minimal examples. Cloning or importing a repository does not execute its notebooks, interpret `databricks.yml`, deploy bundle resources, or install Python packages.

**Pull latest** updates the server's checkout; **Import notebooks** then refreshes the workspace copies. Re-importing the same repository/path replaces that notebook's imported source, including local cell edits. Export or copy changes you want to keep first. There is no automatic commit or push of notebook edits back to Git.

## Format and runtime boundaries

These rules reflect the current [notebook parser](../backend/openbricks/notebooks.py), [Git importer](../backend/openbricks/main.py), and [execution worker](../backend/openbricks/worker.py):

- Git discovery accepts `.ipynb`, `.sql`, and `.py` files whose first 100 characters contain `# Databricks notebook source`. Ordinary Python scripts are not discovered as notebooks. You can upload a standalone `.py` file directly or adapt it into a source notebook.
- Python source notebooks support `# COMMAND ----------` cell separators and `# MAGIC` lines for `%python`, `%sql`, and `%md`. Databricks SQL exports using `-- COMMAND ----------` separators are not split into separate cells; prefer a plain single SQL statement or separate the statements manually in the editor.
- Jupyter Markdown and Python cells import, and a code cell beginning with `%%sql` becomes a SQL cell. Other notebook kernels, arbitrary IPython magics, `%pip`, `%sh`, and `%run` are not translated. Imported outputs are not treated as newly executed results. Notebook limits are 10 MB and 500 cells.
- OpenBricks supplies a managed `spark` session. Review notebooks that create a replacement `SparkSession`, hard-code a master URL, stop Spark, or expect a separate Jupyter kernel. Install compatible libraries on the compute target rather than following another platform's cluster instructions blindly.
- Databricks widgets, secret scopes, task values, cloud mounts, `/databricks-datasets`, SQL warehouses, and Databricks-only APIs need adaptation. The supplied `dbutils.fs` helper is a limited local-blob API: it maps `dbfs:/key` to the local `default` bucket, not a Databricks filesystem. Use `blob.path(uri)` when a Spark operation needs the underlying local path; this alias does not install a general `dbfs:` Spark filesystem driver.
- Relative paths refer to the executing compute process, not automatically to the imported notebook's repository directory. Make datasets available on the selected compute host through an explicit local path or a configured storage connection. A remote compute host needs its own access to that storage.

Review an external notebook before running it, select its compute target, and run the smallest relevant cells first. Use the bundled OpenBricks starters to verify installation, scheduling, packages, and connectors; use these upstream links to learn or adapt specific techniques.
